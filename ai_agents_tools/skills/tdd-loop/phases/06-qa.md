# Phase 6 — QA (independent verdict)

Goal: an independent SHIP/NO_SHIP decision.

## Independence requirement
- If this environment supports sub-agents/tasks with fresh context: spawn the
  QA as a sub-agent whose input is ONLY: the objective, spec.md, plan.md,
  standards context (code-standards skill + rules, OR documented language-default
  fallback per STATE.md), and the repo diff — NOT the conversation history.
- Otherwise: perform the review after an explicit persona reset — evaluate as
  an external reviewer who did not write this code. State this framing before
  reviewing.

## Checks (all mandatory, evidence pasted)
1. **Acceptance immutability (auto-NO_SHIP)**:
   `git diff <acceptance_freeze_sha> -- tests/acceptance/`
   Any output at all → verdict is NO_SHIP with route "implement" and the diff
   as evidence. No exceptions, no judgment call.
2. **Full test run**: acceptance + unit (`python -m pytest tests -q` or repo
   runner). Paste the output.
3. **Standards review** — same loading rules as phase 5 step 1 (Path A or
   Path B). Review implementation + `tests/unit/` only. Do not fix here — QA
   records violations only. If Path B was used, violations must cite
   `rule: "language-default: <language> — <practice>"` and the conversation
   must restate the fallback if not already shown this session.

   For each violation, set `route` on the violation object:
   - **`implement`** (default): typing, docstrings, naming, imports, local
     method structure, file-length fixes within the current layout — fixable
     without changing where components live.
   - **`plan`**: file/module placement, layer or boundary violations, wrong
     package split, missing planned components, responsibility split wrong,
     needs new modules/files not in plan.md — plan.md must change first.

   Paste a concise findings summary in the conversation.

## Verdict — write `<task-dir>/qa-verdict-<N>.json` (N = cycle number; never
overwrite a previous verdict):
```json
{
  "cycle": 1,
  "decision": "SHIP | NO_SHIP",
  "confidence": "high | medium | low",
  "route": "done | implement | plan",
  "standards_violations": [
    {
      "file": "path/to/file.py",
      "rule": "rule name from INDEX",
      "detail": "what is wrong",
      "route": "implement | plan"
    }
  ],
  "gaps": ["non-blocking future improvements"],
  "notes": "concise, not chatty"
}
```

Set top-level `route`:
- `done` only when `decision` is SHIP.
- `plan` when ANY `standards_violations` item has `route: "plan"`.
- `implement` when NO_SHIP, no plan-route violations, but implement-route
  violations remain (or other NO_SHIP triggers with code-only fixes).

Update STATE.md `last_qa_verdict:` to this file's path.

## Routing (orchestrator)
- **SHIP** → `status: done`. Report verdict and violations summary to user.
- **confidence "low"** (regardless of decision) → STOP, show verdict, ask user.
- **NO_SHIP + any violation with `route: "plan"`** → phase 3 (planner triage).
  Present full `standards_violations` to user. Planner reads this verdict,
  updates plan.md for structural items, writes `implement_checklist` in plan.md
  for remaining `route: implement` items. Then phase 4 → 5 → 6.
- **NO_SHIP + all violations `route: "implement"` only** → phase 4 directly.
  Present violations to user. Implementer reads this verdict and resolves every
  item before polish → qa.
- Increment `qa_cycles` before any loop-back. If > 3 → `status: halted`, report.
